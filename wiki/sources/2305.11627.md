## Problem

Existing compression methods for LLMs face two critical constraints: (1) access to the original trillion-token pretraining corpus is impractical (storage, transfer cost, proprietary data), and (2) post-training recovery requires 14+ GPU-days (TinyBERT) or 33+ hours (task-specific BERT), scaling worse at LLM size. More fundamentally, task-specific compression destroys the multi-task generality that makes LLMs valuable — a pruned GLUE-finetuned BERT is worthless as a general-purpose model. LLM-Pruner targets **task-agnostic structural pruning** with minimal data and maximum speed.

## Method

LLM-Pruner operates in three sequential stages:

### Stage 1: Discovery — Build the Dependency Graph

LLMs have **coupled structures**: neurons that are computationally interdependent. Pruning a neuron without pruning its dependents produces broken intermediate representations that cannot be recovered. LLM-Pruner formalizes this as a dependency graph.

**Dependency definition**:
```
N_j ∈ Out(N_i) ∧ Deg⁻(N_j) = 1  ⟹  N_j depends on N_i   (Eq. 1)
N_i ∈ In(N_j) ∧ Deg⁺(N_i) = 1   ⟹  N_i depends on N_j   (Eq. 2)
```

where Deg⁻(N_j) is the in-degree of neuron N_j. A neuron is dependent if it has exactly one incoming source (cannot survive if that source is pruned). Dependencies are **directional and transitive**.

**Trigger algorithm**: Starting from every neuron N_i as a trigger, propagate dependencies iteratively until no new dependent neurons are found. The resulting set forms a **dependency group** — all neurons that must be pruned together. This is fully automatic, no manual architecture analysis.

**Three group types** in LLaMA-style models (Figure 2):
- **Group A (MLP)**: Gate projection → Up projection → Down projection (all must be pruned at the same hidden dimension)
- **Group B (Multi-head Attention)**: Query head h → Key head h → Value head h → output projection neuron (pruning head h removes the corresponding rows/columns across all four projections simultaneously)
- **Group C (Channel-wise)**: LayerNorm → MHA → MLP → LayerNorm (pruning a channel propagates through the full residual block)

The **Block strategy** prunes Group A + Group B simultaneously (treats each MLP+MHA together). The **Channel strategy** prunes Group C only. Block is strongly preferred: Channel forces pruning of first and last layers (which are channel-level structures), destroying critical input/output representations.

### Stage 2: Estimation — Score Each Group's Importance

Given limited access to data, LLM-Pruner uses 10 calibration samples from public datasets (BookCorpus for LLaMA, DailyDialog for ChatGLM). The importance of group G = {W_i}^M_i=1 is:

**Vector-wise importance** (whole-matrix score, Eq. 3):
```
I_{W_i} = |ΔL(D)| = |∂L^T/∂W_i · W_i − ½ W_i^T H W_i + O(||W_i||³)|
```

**Element-wise importance** (Eq. 4–5):
```
I_{W_i^k} ≈ |∂L/∂W_i^k · W_i^k − ½(∂L/∂W_i^k)² · W_i^k|
```

where the diagonal Hessian H_kk ≈ (∂L/∂W_i^k)² is approximated via Fisher information. The gradient term is nonzero because the calibration data differs from the pretraining data.

**Group importance aggregation** (four strategies):
- **Summation**: I_G = Σ I_{W_i}
- **Production**: I_G = Π I_{W_i}
- **Max**: I_G = max I_{W_i}
- **Last-Only**: I_G = I_{W_l} where l is the last executing structure

Empirically, **Element²** (element-wise importance using Eq. 5) with the Block strategy achieves the best results on LLaMA/Vicuna; vector-wise importance is competitive and much faster to compute.

**Layer sensitivity finding** (Figure 3): First and last transformer layers are most sensitive to pruning. Channel strategy unavoidably prunes these layers; Block strategy can skip them (Group A/B structures don't encompass the first/last residual stream). This confirms the Sandwich/Subformer insight for pruning — middle layers are most compressible.

### Stage 3: Recovery — LoRA Fine-tuning

After removing the lowest-importance dependency groups, the pruned model is fine-tuned with LoRA:

```
ΔW = PQ,   P ∈ ℝ^{d⁻ × d},   Q ∈ ℝ^{d × d⁺}
f(x) = (W + ΔW)X + b = (WX + b) + (PQ)X   (Eq. 6)
```

Only P and Q are trained — the pruned W is frozen. **Training recipe**: 50K samples from the Alpaca dataset (publicly available), 2 epochs, ~3 hours on a single GPU. P and Q can be re-parameterized into ΔW without adding permanent parameters.

## Results

### LLaMA-7B, 20% Parameter Reduction (Table 1, 7 zero-shot classification datasets)

| Method | WikiText2 PPL | PTB PPL | Avg. Zero-Shot Accuracy |
|--------|-------------|---------|------------------------|
| LLaMA-7B (dense) | 12.62 | 22.14 | 68.59% |
| L2 pruning, no tune | 582.41 | 1022.17 | 42.65% |
| **Block + Element², no tune** | **17.37** | **30.39** | **56.82%** |
| **Block + Element², with tune** | **15.18** | **28.08** | **60.07%** |

With LoRA recovery: **60.07% avg = 94.97% of the original model's performance** at 80% of original parameters.

### Vicuna-7B, 20% Parameter Reduction (Table 4)

| Method | WikiText2 PPL | Avg. Zero-Shot Accuracy |
|--------|-------------|------------------------|
| Vicuna-7B (dense) | 16.11 | 62.78% |
| Block + Element², no tune | 25.74 | 56.25% |
| **Block + Element², with tune** | **19.69** | **57.78%** |

57.78% = **92.03% of original Vicuna-7B performance** at 80% of parameters.

### ChatGLM-6B, 10% Reduction

Vector-wise importance with LoRA tune: 47.34% accuracy = **100.62% of original** (slight improvement from fine-tuning regularization effect).

### Memory and Latency (Table 3, LLaMA-7B)

| Strategy | Ratio | Parameters | Memory | Latency |
|----------|-------|-----------|--------|---------|
| Dense | — | 6.74B | 12884.5 MiB | 69.32s |
| Block (Channel) | 20% | 5.39B | 10363.6 MiB | 61.50s |
| Block (Block) | 20% | 5.42B | 10375.5 MiB | 58.55s |

20% block pruning: **−20% parameters, −19.5% memory, −15.6% latency** without any sparse hardware.

### Pruning Rate Sensitivity (Figure 4)

- LLaMA-7B: magnitude-based methods collapse at 20% pruning; LLM-Pruner holds up to 60% with acceptable perplexity
- At 50% pruning without tune: severe degradation; LoRA recovery is insufficient at very high ratios — LLM-Pruner recommends ≤30% as the practical safe range

## Significance

- **First task-agnostic structural pruning framework for LLMs**: removes the billion-parameter corpus requirement; uses 50K public samples; recovers in 3 hours on one GPU
- **Dependency graph formalism**: the automatic detection of coupled structures (which neurons must be pruned together) is the key algorithmic contribution; without it, structural pruning of LLMs produces broken architectures
- **Block > Channel conclusively**: the first/last layer sensitivity finding (Figure 3) is a direct empirical confirmation of the Sandwich/Subformer theoretical result — the same layers that cannot be shared cross-layer are the same layers that cannot be pruned without severe degradation
- **LoRA as universal recovery**: 50K samples and 3 hours is a practical standard for post-pruning recovery that subsequent work (BESA, LoRAPrune) builds on
- **For HaLViT**: LLM-Pruner's dependency detection is directly applicable but requires extension for shared weights. HaLViT's Wkv is used for both key projection (W→x) and value projection (Wkvᵀ→x'). Standard dependency detection treats these as separate nodes. A correct dependency graph for HaLViT must add a **W+Wᵀ coupling edge**: when row i of Wkv is identified as part of a dependency group (Key head h), the same rows of the Wᵀ path (Value head h) must be included in the same group. For head-level Group B pruning, this coupling is automatically satisfied — removing head h removes its row block from Wkv for keys AND the transposed row block for values. The LoRA recovery path is also enhanced: a LoRA adapter (PQ) added to shared W covers both the W→x path (WX + PQX) and the Wᵀ→x' path ((Wᵀ + QᵀPᵀ)X') — one adapter serves both roles, making recovery more parameter-efficient under weight sharing.
